# 不同架构皮肤站的适配判断

## 先回答能力而非框架名称

一个皮肤站能提供 OAuth 用户资料，并不代表能验证 Minecraft 进服。需要找到与 access token、角色、serverId 绑定的权威会话校验。没有它时，网关必须通过明确授权的主站扩展获得能力，或在目标架构下实现完整认证会话服务；不能用一次资料查询或公开 profile 返回代替 hasJoined。

分析结果应以“已具备、需要适配、需要新增、待中心确认”描述，不因目标是 PHP、Java、Go、Python 或 Node 就推断结论。

## 架构选择

| 目标现状 | 优先方案 | 必须补齐 |
| --- | --- | --- |
| 已有安全 Yggdrasil，主站不便改动 | 独立网关 | 路由、材质重签、成员控制、目录、角色同步 |
| 已有 Yggdrasil 且允许原生扩展 | 原生集成或网关，按用户选择 | 确保 Union 密钥生效和原有身份边界 |
| 已有安全账号体系，但没有 join 会话 | 最小主站扩展加适配器，或明确范围内的新数据面 | token 与角色绑定、serverId 会话、有效期和权限校验 |
| 只有公开角色/材质查询 | 先补认证契约 | 不能把无鉴权查询包装成联合进服成功 |
| 已有 Union 成员实现，只换存储或语言 | 按精确契约迁移 | 保留 UUID、成员凭证、生效代次、同步与拒绝语义 |
| 仅网站使用 Union OAuth 登录 | 普通依赖方接入 | OAuth 回调、state、token 验证；不部署成员签名网关 |

不要为了统一架构，要求目标站增加并不需要的通用密钥管理。若共享密钥留在网关，网关自己负责换钥即可；若主站签名器实际持有共享密钥，才需要主站加载或远程 signer 能力。

## 外置网关的边界

主站负责账号认证、token 轮换、角色归属、封禁和进服权限。网关负责对外 Union 协议、身份适配和出口签名。上游错误不能转换成成功；上游超时也不是“角色不存在”。

启动器使用网关的认证根，让它获取一致的签名公钥与域名列表。仅把服务器 hasJoined 指向网关、启动器仍使用旧 metadata，无法保证跨成员材质可见。

不要读取主站私有数据库或 Redis 来绕过 API；如果用户明确采用原生集成，则遵守目标站自身分层和权限模型。外置模式发现缺接口时，应列出最小接口与授权需求。

代理只允许指定路由到固定上游，限制 body、超时、重定向和并发。账号密码与 token 不进入访问日志。若主站支持后端聚合或 fallback，必须核对返回 profile 是否为当前成员拥有的本地角色，不能把任意第三方响应重新签成成员角色。

特别检查“本地主站拒绝后继续 fallback”的分支：一次成功 join 与相同 UUID 也不能独立证明后续 200 来自本地会话。优先使用能区分本地成功的权威接口；若采用来源关联，必须按目标真实会话有效期限制窗口，并重新向主站验证原 token，覆盖撤销、刷新、到期和重启。短期 token 不进入持久化库，来源关联始终不能替代主站授权。

## 身份建模

优先保留目标站稳定内部 ID，分析它是否与 Minecraft UUID 共用同一字段。如果共用字段同时被外键、token 和授权引用，不要直接改主键来模拟 PHP 的独立 uuid 表。

独立网关可建立 local_profile_id 与 union_uuid 的结构化映射，并保存映射状态与修订。所有往返请求必须做一致转换；同名角色属于不同成员时不能只用名称作为全局主键。

未来接入其他站时，内部 ID 可能是整数、UUID 或不可变字符串。仅向 Union 暴露符合协议的身份，别把本地 ID 强行当作 Union OAuth 的 uid 或 Minecraft UUID。

首阶段支持无冲突、未绑定角色可以减少实现范围，但仍须识别和拒绝冲突状态。未经中心确认不能假定每个原始 UUID 都被原样保留。

## 配置与运行状态

配置保存部署意图，状态保存已提交的运行事实。listen address、内部主站 API 根、公开登记根是三个独立概念。

材质密钥代次至少记录 remote_version、公钥规范化指纹、受保护的私钥引用与实际 active 状态。密钥文件写入成功不等于全部 worker 已切换；需要一致快照或等效的原子切换与重启恢复。

成员凭证变更要覆盖实际请求使用的值，不是只改状态页面。中心公钥与材质公钥分别管理，任何缓存过期处理都不能变成跳过验签。

生产凭证明确提供，示例不带可用密钥；测试依赖通过构造器注入。有限轮询可补偿中心通知丢失，但不能伪造历史版本或撤销协议。

## 同步与权限

通过目标站已支持的服务应用或等效权限读取全站角色。用户授权 token 只能读取用户拥有的角色时，不能称为全站权威同步。

枚举接口精确处理 cursor、page 或 offset，直到权威完整快照读取成功。所有页不是一个一致快照时，结合变更事件与最终对账修复竞态，不能宣称读取过程天然事务一致。

若没有事件系统，初期可以使用有界轮询和全量对账。若有事件，验证签名、权限、至少一次语义、乱序、删除后的回查和失败重试。Webhook 禁止内网是目标站策略时，应调整接收部署或选择轮询，不静默放宽 SSRF 限制。

绑定与邮箱查询是另外的数据授权面。用户能登录网关不代表能操作任意 UUID，也不代表可以查询其他用户邮箱。中心是否要求这些能力需由成员准入和真实协议证据决定。

## 交付矩阵建议

记录目标站实际文件和精确 endpoint；不要只写“对接 API”：

| 能力 | 目标站来源 | 适配责任 | 状态 |
| --- | --- | --- | --- |
| 登录和刷新 | 实际 handler/service | 转发或原生调用，保留 token 语义 | 已具备或需新增 |
| join 和 hasJoined | 实际会话实现 | 权限及 serverId 验证 | 已具备或需新增 |
| 角色全量与事件 | 实际枚举和事件 | 同步、去重、删除、对账 | 已具备或需新增 |
| 元数据和签名 | 实际 signer 与根响应 | 出口公钥、域名和重签 | 适配 |
| UUID 映射 | 数据模型、token 引用 | 完整往返转换 | 范围内实现或明确限制 |
| 成员控制 | 参考协议 | 验签、凭证、目录、密钥代次 | 适配 |
| 真实 Union | 获准测试成员 | 登记与真实游戏验证 | 待联调或已验证 |
