# Element Skin Union 网关实现方案

## 背景与决定

Element Skin 已有 Yggdrasil 认证、角色查询、进服会话、细粒度权限、OAuth Client Credentials 和角色 Webhook。它的 Yggdrasil 密钥在启动时加载，没有对外的密钥版本管理或热切换接口。

首阶段采用独立网关：Element Skin 保持账号、角色和会话权威；网关持有 Union 共享材质私钥，提供 Blessing 风格成员路径，代理认证并重签经过验证的角色属性。网关不依赖替换 Element Skin 密钥，不直接访问主站数据库或 Redis。

当前是设计阶段。下文的数据表、模块、管理 API 和配置均为拟实现契约，不代表已有运行能力。协议事实见[证据记录](协议证据与待验证项.md)，通用线上协议见[Union 协议参考](../skills/union-skill/references/union-protocol.md)。

## 目标

- 无冲突、未绑定的 Element Skin 角色能通过真实 Union 服务器完成联合进服。
- 网关使用共享私钥输出可被 Union 客户端接受的材质，且继续执行主站权限与封禁策略。
- 共享密钥和成员凭证支持网关独立更新、重启恢复及精确的生效状态报告。
- 角色全量及增量同步最终一致，网络失败和重复通知不制造错误状态。
- 将跨架构的适配方法整理为可复用 union-skill，具体实现先服务于 Element Skin。

## 首阶段非目标

- Union OAuth、绑定和解绑界面、联合黑名单管理后台。
- 向 Element Skin 原生入口强制写入 Union UUID 或共享密钥。
- 对未知中心协议做猜测式兼容，伪造 Blessing 插件版本或无条件声明功能支持。
- 多实例部署、共享状态数据库、通用插件市场、生产自动部署。
- 在首次进服验证中处理名称或 UUID 冲突、跨站绑定。检测到这些状态时明确拒绝受影响角色，不能静默使用错误身份。

这些范围不豁免中心实际要求的访问策略。如果中心要求 queryemail、联合黑名单检查或其他能力才能接入，应记录具体证据并调整范围，不能为通过登记返回虚假结果。

## 请求与信任边界

    启动器
      → 网关 /api/yggdrasil/authserver/*
      → Element Skin /authserver/*

    客户端 join
      → 网关 /api/yggdrasil/sessionserver/session/minecraft/join
      → Element Skin /sessionserver/session/minecraft/join

    Minecraft 服务器 hasJoined
      → Union 中心 /api/union/yggdrasil/...
      → 网关 /api/yggdrasil/sessionserver/session/minecraft/hasJoined
      → Element Skin /sessionserver/session/minecraft/hasJoined
      → 网关核对角色、使用 Union 密钥重签
      → Union 中心 → Minecraft 服务器

中心转发到成员的确切 URL、参数和映射顺序仍需真实联调。不能因 PHP 成员提供该接口就认定中心实现细节已被证实。

启动器的本次认证入口必须是网关。若使用 Element Skin 原生入口，客户端缓存的签名公钥和域名列表仍属于主站，不能保证接受 Union 材质。

网关只转发预先登记的路由到固定上游，不提供任意 URL 代理，不跟随认证请求到其他 origin 的重定向。上游拒绝、超时、返回畸形资料或未知角色时不得生成成功 profile 或材质签名。

## 数据模型

单实例使用 SQLite 保存结构化状态，私钥与成员凭证位于受保护的本地 secret 目录。时间统一为毫秒。密钥文件名由程序生成，不从回调 payload 拼接路径。

| 表 | 关键列与约束 |
| --- | --- |
| signing_generations | id 主键、remote_version、fingerprint_sha256、private_key_ref、created_at_ms；版本与指纹冲突必须显式处理 |
| gateway_state | 固定单行 id=1、active_generation_id 外键、active_member_credential_ref、directory_version、last_reconciled_at_ms |
| union_members | code、root_url 联合主键，支持当前目录中同 code 多 root 的现实情况；独立保存目录域名集合 |
| local_profiles | local_id 主键、name、synced_name、revision、deleted_at_ms、last_synced_at_ms |
| callback_nonces | nonce 主键、expires_at_ms；验签通过后以唯一插入原子占用 |
| webhook_receipts | event_id 主键、profile_id、event_type、received_at_ms；成功持久化任务后才确认接收 |
| sync_jobs | id、profile_id、operation、source_revision、attempts、next_attempt_at_ms、state、last_error_code |

首阶段 local_id 就是提交给 Union 的 UUID，不建无用途的映射表。后续需要映射时引入有唯一约束的 local_id 与 union_id 关联，不能在 JSON 配置中保存映射。

目录从 root_url 提取 hostname，不能把含路径的根 URL 直接填入 skinDomains。实际材质使用独立 CDN 时，必须单独核实并加入受控域名集合。

## 密钥生效与故障恢复

必须区分 remote_version 与 active_version。hello 和管理状态中的已启用版本来自实际签名快照，不来自最近一次下载结果。

更新顺序：

1. 用当前成员凭证从固定中心拉取共享私钥及版本，限制大小与超时。
2. 解析 RSA 私钥，验证结构；从私钥派生公钥，并与中心联合认证入口公布的材质公钥比较规范化 DER 指纹。
3. 版本相同且指纹相同视为幂等；版本相同但指纹不同、版本回退、公钥不匹配均拒绝，保留现有代次。
4. 写入新的不可变密钥代次文件，限制文件权限；同步落盘后提交 SQLite 代次与 active 指针。未引用的文件可在明确的恢复流程中清理。
5. 用同一写锁保护持久化提交和内存快照发布。签名、元数据、公钥端点与状态读取相同的 active 快照。
6. 成功后才确认更新。失败不修改生效版本；进程重启从数据库已提交的 active 指针恢复，不能重新生成一个自有密钥冒充 Union 密钥。

单次请求的一致性不等于已启动客户端自动更新信任。中心缺少已证实的双钥过渡和撤销契约；轮换时需通过联调确定客户端重启或刷新要求。

中心验签公钥与材质共享私钥分别管理。公钥从固定 HTTPS 中心获取只提供 TLS 绑定的信任，不能写成具备独立离线签名的密钥链。公钥变更、缓存失效和中心不可用时的行为需要明确记录。

成员凭证更新也使用不可变 secret 文件与 active 引用，禁止只更新数据库字段而请求代码继续使用启动配置中的旧值。

## API 与代理规则

| 入口 | 首阶段行为 |
| --- | --- |
| GET /api/yggdrasil | 网关元数据，使用 active Union 公钥和允许域名列表 |
| POST /api/yggdrasil/authserver/authenticate | 转发主站认证，验证响应结构，首阶段维持本地身份 |
| POST /api/yggdrasil/authserver/refresh | 转发刷新，保留 token 绑定规则 |
| POST /api/yggdrasil/authserver/validate、invalidate、signout | 精确转发对应协议 |
| POST /api/yggdrasil/sessionserver/session/minecraft/join | 主站授权成功才成功；保留 serverId 与角色语义 |
| GET /api/yggdrasil/sessionserver/session/minecraft/hasJoined | 仅对主站验证成功的本地角色响应重签 |
| GET /api/yggdrasil/sessionserver/session/minecraft/profile/{uuid} | 查询并核对本地角色，按 unsigned 语义签名 |
| 角色名查 UUID、批量查询、minecraftservices 别名 | 按参考客户端和所选客户端实际需要提供精确映射 |
| 公钥发现端点 | 输出本次入口使用的 Union 材质公钥，不透传主站原始公钥集合 |
| GET /api/union/member/ | 当前目录版本、实际生效私钥版本、真实功能声明 |
| POST /api/union/member/updatelist、updateprivatekey、updatebackendkey、sync、diagnose | 验签、原子防重放、执行业务后响应 |
| POST /api/union/member/remapuuid | 首阶段不修改主站；明确报告未支持并将受影响角色标记为待处理 |
| POST /webhooks/elementskin | 校验主站签名、去重、持久化同步任务 |
| GET /health/live、/health/ready | 区分进程存活与签名、目录、凭证准备就绪；不泄露敏感状态 |

公钥发现路径需对照目标 authlib-injector 版本核实，不能臆造统一路径。Yggdrasil 错误保留协议格式；上游不可用产生明确的网关错误，不能把超时转换为“未加入”或 200。

材质重签名签的是 properties.value 原始 Base64 字符串的字节，算法为 RSA PKCS#1 v1.5 与 SHA-1。若修改内部 profileId、profileName 或材质 URL，先按规范编码新的 value，再签这个新值。SHA-1 只用于该既有材质协议，不复用到中心回调验签。

不删除 SKIN 的 slim metadata 或 CAPE，不泄露主站签名到网关公钥接口；所有带 signature 的属性都必须与出口公钥对应。无签名要求的查询保留 unsigned 语义。

首阶段管理使用有界的 CLI 操作或仅受保护的管理端点，提供 sync、refresh-directory、refresh-key 和 status，不先建设管理页面。认证机制及外部可达范围在实现这些入口前明确，不复用普通用户 token 作为全站管理权限。

## 角色同步

服务应用通过 profile.read.any 获取所有角色，分页参数使用 cursor。全量 payload 为 profileList 的 UUID 到角色名对象；成功读取全部页面后才提交全量，失败不能用部分列表覆盖中心。

增量事件只作为变更提示。网关收到合法 Webhook 后持久化任务，再确认事件；worker 回查当前权威状态。每角色串行协调，重复事件合并，乱序事件不能复活已删除角色。创建后立即删除、中心已存在、更新时中心尚不存在等情况以实测响应决定收敛动作，不猜测错误码。

定期全量对账修复漏事件。首次快照与事件订阅存在竞态，使用“先接收事件、再读全量、重放待处理任务、最后对账”的顺序。主站不可用时不执行推断删除。

本地重试属于网关责任，不要求 Element Skin worker 无限重试。删除 tombstone 保留有界时间，以支持失败重试；清理条件与中心确认状态关联。

## 配置与部署

| 配置概念 | 要求 |
| --- | --- |
| listen_addr | 部署配置，可监听回环或容器网络 |
| public_root | 已登记的 HTTPS 成员根地址，可包含经验证的子路径 |
| elementskin_api_url | 固定上游 API 根，内部地址可配置 |
| elementskin_site_url | 仅用于明确的用户页面链接，不用于推导 API 地址 |
| service_client_id / secret_ref | 主站机密应用，最小必要权限 |
| union_member_credential_ref | 从中心登记流程取得或经中心签名回调更新 |
| state_path / secret_dir | 显式路径、受限权限、备份与恢复边界 |
| webhook_secret_ref | 主站实际发放的签名 secret，不假定调用方可以自行指定 |
| timeouts / body_limits | 有限请求大小、超时、重试和并发限制 |

生产中心固定为 https://skin.mualliance.ltd/api/union，不暴露任意 hub_url 设置。离线测试通过构造器注入模拟中心。配置样例在代码实现时提供，真实凭证和文件不进入仓库。

对外必须保证成员路径稳定，不要求固定 IP。反向代理可把公开路径映射到网关任意监听地址；不要把内部 root_path 改写当作中心已支持任意回调路径。

Element Skin 当前 Webhook 禁止内网及回环目标。网关接收事件需提供符合主站策略的 HTTPS 地址；不能为 sidecar 便利静默放宽主站 SSRF 规则。

## 用户交互

首阶段用户只需要添加网关认证地址并使用原有账号登录。网关元数据可链接主站注册页面，不增加独立账号注册或口令保存。

管理员能区分“成员已登记”“目录已同步”“签名代次已生效”“角色已同步”“真实进服已验证”。状态页面或日志中的同步成功不能替代进服结论。发生身份冲突时提供明确的角色处理提示，不自动修改用户 Minecraft 存档身份。

## 开发顺序与验收

| 阶段 | 交付 | 完成条件 |
| --- | --- | --- |
| M0 文档初始化 | 当前仓库、协议证据、设计与 union-skill | 技能验证通过，内部文档链接有效 |
| M1 主站代理 | 路由映射、认证及 join/hasJoined 代理 | 使用模拟依赖验证精确请求和上游拒绝传播 |
| M2 签名与成员控制 | 签名代次、元数据、公钥、目录、回调 | 验证重签与运行代次一致，故障恢复不报告虚假成功 |
| M3 角色同步 | 服务应用、全量、事件任务和对账 | 多页不丢失，重复和乱序收敛，失败不提交部分全量 |
| M4 真实链路 | 真实 Element Skin、获准测试成员和游戏客户端 | 同一身份完成联合进服，材质可见，拒绝和封禁仍生效 |

详细测试见[测试与联调计划](测试与联调计划.md)。M1 的模拟依赖不能替代 M4；在真实中心测试前需完成 M2、M3，避免向中心提交不完整成员状态。

## 待确认问题

- Union 是否接受非 Blessing 实现、网关自身版本号及受限功能声明。
- 中心转发路径、hasJoined 的参数与 IP 处理、目录和材质域名更新行为。
- 中心如何处理无绑定但存在名称或 UUID 冲突的成员，以及 remapuuid 是否在首次登记就触发。
- 共享密钥轮换的生效时机、客户端缓存过渡与泄露后的撤销行为。
- 第一阶段是否必须实现 queryemail 或黑名单相关能力；如需要，必须明确数据授权和进服语义。
- Element Skin 30 秒 join 会话在真实中心转发延迟下是否足够。
